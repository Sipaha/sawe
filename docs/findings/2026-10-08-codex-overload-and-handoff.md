# Codex overload recovery and premature handoff

The 2026-10-07 incident in session `jh7enjs3` did not exhaust the context.
The editor sent its first 40% notice at 23:01:08 +0700. Codex ended the main
turn with `server_overloaded` at 23:04:50; the handoff directory `c02` was
created at 23:04:53. The turn ended due to provider failure while the Push
changes were still being verified.

The handoff ladder used absence of busy work as an immediate Force shortcut.
An error releases the prompt future too, so it bypassed the two 15-minute
escalation windows. Idle or background-only activity is not proof that the
user's phase has finished.

`HandoffLadder::end_turn_observed` now permits an automatic idle handoff only
after a main `EndTurn`. Main messages, external starts, errors and load errors
invalidate that proof. Without an active main turn or successful completion,
the automatic ladder stays parked, even if side-channel activity labels the
session Running. Explicit user compaction, successful completion, Stop, and
the existing escalation windows retain their behavior.

Codex CLI 0.160.1 exposes `willRetry` in its generated ErrorNotification schema.
Sawe leaves those nonterminal notifications to Codex. Only a terminal failed
turn with `codexErrorInfo: serverOverloaded` gets the additional recovery:
three continuations after 10, 20 and 40 seconds, with less than one second of
jitter. The conversation, selected model and reasoning effort are retained.
A runtime recovery notice asks the agent to reconcile completed steps and
continue remaining authorized work; the accepted original input is not resent.

The client completion remains pending throughout recovery; autonomous turns
remain active as well. Stop cancels a waiting recovery immediately without
killing the connection. Generation and turn-id guards protect late events.
After exhaustion, the failure is surfaced normally. Account token/quota limits
(`usageLimitExceeded`), billing/authentication failures and other error kinds
never enter this additional retry loop.

Sources: [Codex app-server](https://learn.chatgpt.com/docs/app-server),
[OpenAI error codes](https://developers.openai.com/api/docs/guides/error-codes),
and the schema generated by the installed Codex CLI.

Verification: the provider-failure regression failed before the change.
All 1007 solution_agent tests passed (one ignored), including 19 handoff tests;
all 24 codex_native tests passed. Nine native-headless mock app-server scenarios
passed: client recovery, autonomous recovery, client/Goal cancel and connection reuse,
queued input, authentication failure, account quota, native `willRetry`, and
retry exhaustion at 41% context. Exact start/steer counts verified no original
input replay or duplicate delivery. The exhausted case made exactly four
starts and remained Errored without a compaction prompt; quota made one start.
The waiting UI was screenshot-verified. Scratch evidence lives in the
Solution's `.tmp/retry` directory.
